# v0.9 integration: browser, XR streaming, bundled host, multi-monitor

> Status: Active (2026-10-23). The four features exist as prototypes on
> separate branches; this plan brings them onto one branch for v0.9.

## Where each feature lives

| Feature | Branch | Base | State |
| --- | --- | --- | --- |
| Inbuilt browser | `feat/unified-content-tabs` | v0.8.1 (`main`) | 11 commits; shipped as v0.8.2-preview.1 |
| XR streaming | `feat/meteor-xr-streaming` | the browser branch | 35 commits on top of the browser, in progress |
| Bundled GameStream host | `feat/meteor-bundled-host` | `main` + `fix/pairing` | Meteor runs a dev Vibepollo build; no release build yet |
| Multi-monitor, headset | already on `main` | | Monitors tab speaks the Polaris display API |
| Multi-monitor, host | Vibepollo fork, `feat/multi-monitor` | `linux-x11-nvfbc-pyrowave` | X11 only; untested on a real stream |

Two facts make this simpler than it looks:

- **The XR branch already contains the browser.** Every browser commit is
  an ancestor of `feat/meteor-xr-streaming`, so merging XR brings both.
- **Multi-monitor needs no headset changes.** It ships inside the bundled
  host (the fork answers `/polaris/v1/display/manifest` and `outputs=`).

## Branch model

- **`main` stays releasable.** User feedback is fixed on short branches
  off `main` (`fix/user-feedback` first) and released as 0.8.x.
- **`integration/v0.9`** is the one branch where all four coexist. It is
  created when XR is feature complete, and lands on `main` as v0.9.0.
- **Merge, don't rebase.** `feat/unified-content-tabs` and
  `feat/meteor-xr-streaming` are pushed; rebasing them would rewrite
  shared history.
- **Merge `main` forward often.** After each 0.8.x release, merge `main`
  into the XR branch (which carries the browser) and into
  `feat/meteor-bundled-host`, so feedback fixes never collide late.

## Order

1. **Now: feedback fixes on `main`.** Small PRs from `fix/user-feedback`.
   A fix to browser behaviour goes on `feat/unified-content-tabs` instead,
   since the browser isn't on `main` yet; v0.8.2-preview users run it.
2. **Land `fix/pairing` on `main`.** One commit, independent, and the
   bundled host needs it. Do this early so the host branch shrinks to its
   own work.
3. **Finish XR** on `feat/meteor-xr-streaming` (unchanged; the browser
   comes with it).
4. **Create `integration/v0.9`** from the finished XR branch, then merge
   in order:
   1. `main` (the 0.8.x fixes);
   2. `feat/meteor-bundled-host`.
5. **Fork release.** In github.com/tB0nE/Vibepollo, make branch
   `nightfall` = `linux-x11-nvfbc-pyrowave` + `feat/multi-monitor`, build
   the self-contained Linux tarball (bundled-host plan, Phase 1), and pin
   its URL and SHA-256 in `meteor/src/host/install.rs`.
6. **Verify** (below), then merge `integration/v0.9` into `main` and
   release Nightfall v0.9.0 with the matching Meteor.

## Known conflicts

A trial merge of `feat/meteor-bundled-host` into the XR branch (at
`ef1a153`) stopped on two files; everything else merged cleanly.

- **`meteor/src/main.rs`, shutdown.** XR added an async `Shutdown`
  coordinator (`quit()` requests, `finish_quit()` exits after XR cleanup).
  The host branch made `quit()` stop the bundled host and added a restart
  path (`RESTART_ENV`). Resolution: keep XR's coordinator; stop the
  bundled host and the virtual microphone inside `finish_quit()`; keep
  `RESTART_ENV` for restarts.
- **`test/test_welcome_screen.gd`.** Both sides added tests to `_init()`;
  keep all of them.

Expect more in `meteor/src/main.rs` and `src/stream_manager.gd`: the XR
branch has uncommitted work in both. Re-run the trial merge before step 4.

## Overlaps to resolve on purpose

- **Process supervision.** The host's `meteor/src/host/supervisor.rs`
  copies the `OwnedProcess` pattern from `meteor/src/xr_session.rs`
  (process group, SIGTERM then SIGKILL). Move it into one shared module
  after the merge.
- **Ports.** XR adds Meteor services; the bundled host derives its ports
  when another host holds 47989. Check the firewall rules
  (`meteor/src/firewall.rs`) cover both sets.
- **Screens.** The browser adds multi-screen workspaces
  (`src/screen_sources.gd`, `src/screen_manager.gd`); the Monitors tab
  places one screen per host monitor. Decide how a host monitor appears
  among browser tabs, and test both at once.
- **Who owns the desktop.** XR hands desktop presentation to a running XR
  session; the bundled host may be the one streaming that desktop. Test
  an XR launch while the bundled host streams.

## Open issues to close before v0.9.0

- Audio stopped playing on the PC while two Meteor and host stacks ran;
  not root-caused.
- Meteor's microphone cleanup can unload a module id that PipeWire has
  reused.
- Multi-monitor on Wayland (KWin, portal) and virtual monitors are not
  ported; v0.9 can ship X11 only.
- One-click pairing (bundled-host plan, Phase 4).

## Verification

- **Automated:** the GDScript suite (`test/run_gdscript_tests.sh`),
  `cargo test --no-default-features` in `meteor/`, and the fork's unit
  tests (`test_component_linux_display_manifest`).
- **On the Quest 3:**
  - desktop stream through a stock host and through the bundled host;
  - browser tabs alongside a desktop stream;
  - an XR launch from the wristwatch, and back to the desktop;
  - two monitors selected in the Monitors tab, including mouse input;
  - USB Link.
- **Fresh Linux account:** install Meteor, set up the bundled host, pair,
  and stream, with no other host installed.
